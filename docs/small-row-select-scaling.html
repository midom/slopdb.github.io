Scaling small-row SELECTs beyond the initial cache fixes

This follows the initial LRU/CLOCK comparison. The next optimization report covers subsequent point-index decoding, private buffers, cache admissions and catalog gate changes; the measurements below retain their original source fingerprints. The baseline here is that already optimized implementation, with 16 cache shards. It is not the original 940d63d baseline. Measurements use the same 39,062,500-row, 10,000,000,000-logical-byte seed on test, 100 independent sessions and checked prepared full-row primary-key SELECTs. The seed remains at /home/ubuntu/slopdb-small-row-10gb.

The host has 60 ARM Neoverse-N1 cores and approximately 58 GiB RAM. An independent six-second allocation-free CPU control consumed 59.96 CPU cores. The inspected cgroups had unlimited CPU quotas and no recorded throttling. Go uses all 60 execution slots; their being busy does not mean all time produces useful SQL work. Per-sample user/system CPU seconds now distinguish useful throughput, CPU consumption and wall-clock waiting.

Changes and why they help

  1. More independent cache admissions. Increase the decoded-block cache from 16 to 128 padded shards, keeping the total byte budget unchanged. Miss insertions and LRU refreshes no longer queue so many readers behind the same writer lock. CLOCK and LRU retain their existing eviction rules. Capacity remains partitioned: a decoded allocation larger than its shard budget bypasses admission, and skew can leave some shards underused. These runs use 4 KiB physical pages, which fit comfortably in every tested shard budget.

  2. Distributed read-view references. SQL point reads use their stable reader IDs to choose one of 64 registration locks and padded reference counters. This replaces shared viewMu reader-count updates and global view-reference updates on each point read. Publication excludes all registrations in fixed order before retiring a view. A retired view releases its file pins exactly once, after both legacy and distributed references reach zero. Disk reads still hold no publication lock, and returned bytes remain caller-owned.

  3. Remove an unnecessary snapshot gate. Snapshot registration already holds the bucket lock used by the compaction cutoff walker. Read the published watermark and register under that lock, without also updating global viewMu reader state. The cutoff captures its watermark before walking buckets: a later registration either appears in the walk or reads a sequence at least as new as the cutoff. Legacy snapshot registration uses the same argument under snapshotMu. Version retention stays enabled.

  4. Distribute shutdown bookkeeping. Stable session IDs select one of 128 padded execution-reader counters. Database shutdown publishes writer intent and checks every counter before entering. Readers still register before rechecking writer intent, and cancellable slow waits retain writer preference. A lock waiter releases and reacquires its original counter. The legacy gate remains available for metadata/maintenance calls. The preceding diagnostic attributed about 7.5% of sampled CPU to the old global reader increments and decrements after the storage-view bottleneck had been removed.

  5. One cancellation context for the common case. Calls without a configured query timeout share one cause-aware cancellation context for session shutdown and transaction aborts. This avoids a second nested cancel context, its child map and extra Done channel. Explicit deadlines keep their existing timeout path. Parent cancellation, abort causes, publication rollback and streaming Rows lifetimes retain their normal behavior.

  6. Compile simple point projections. Eligible prepared physical-table reads reuse validated projection metadata rather than allocate a copied SELECT AST, expression projection and general key-batch scaffolding on every execution. Each result still receives its own column metadata, row map and BLOB data. Runtime bindings, residual predicates, LIMIT/OFFSET, transaction overlays and normal statement snapshots remain active. Qualified/aliased expressions, joins, ordering, grouping, locking reads and query instrumentation retain the general path. Catalog/statistics changes invalidate the compiled recipe.

  7. Reuse private point-lookup scratch. Borrow index/data key buffers from a sync.Pool. These buffers never back returned values. Discard oversized scratch rather than retain arbitrary large user keys in the pool.

Measurement and runtime headroom

Additional 20 GB, 100-reader controls kept the same binary and reduced only GOMAXPROCS. With default GC, 16 execution slots reached 1.23M SELECTs/s and 32 reached 1.94M, below the 60-slot matrix's 2.26M. With extra GC headroom, 32 slots reached 2.34M versus 2.91M at 60. These exploratory 20-second controls support retaining all 60 slots; restricting concurrency is not the scaling fix.

The default-runtime cache matrices retain three consecutive 30-second samples per fresh process and the earlier stride-eight checked warmup. CLOCK runs first, then LRU. A separate CLOCK scaling curve uses 1, 8, 16, 32, 60 and 100 readers, with two 15-second samples per process at the fully fitting 20 GB cache. The exploratory pre-change curve used one 12-second sample per reader count. These are descriptive observations from one fixture and ordered runs, not independent replications or a statistical significance claim.

The database/CPU settings, Go 1.26.0 compiler, 4 KiB pages, deterministic key seeds and full-result validation stay fixed. Linux filesystem caching remains enabled and is never reset. This is not a cold-device random-I/O test. Every matrix hashes all SSTables before and after, rejects query failures, changing sequence numbers or excess cache occupancy, and matches the original seed's full inventory.

CPU profiles after the lock changes show allocation and runtime sweeping as a remaining limit, even while Go reports no idle execution slots. The library does not change process-global GC settings. Separate runs explicitly set GOGC=200 GOMEMLIMIT=46GiB on this 58 GiB host to measure additional GC headroom. These settings can increase resident memory substantially; their results are reported separately from code-only/default-runtime gains. Peak RSS includes warmup, decoded cache metadata, active results and Go heap headroom, not just the configured decoded-page budget.

Separate 15-second diagnostics show about 4.77 aggregate seconds of sampled query mutex waiting over 21.45 million fully cached baseline queries, versus 1.47 seconds over 31.71 million queries in the frozen final build. Shared atomic cache-line traffic is visible in CPU profiles rather than these blocked-time totals. At 10 GB, cache-admission locks still block readers: final diagnostics attribute about 386 aggregate seconds over 36.37 million queries with default GC, and 377 seconds over 47.52 million with extra headroom. Concurrent waiting times are summed and must not be mistaken for elapsed wall time.

The retained CPU and blocking reports show the remaining costs. Diagnostic throughput is excluded from the result tables. Heap allocation profiles are cumulative from process startup, including warmup; per-query allocation comparisons use timed-sample counters.

Correctness and reproduction

Permanent tests cover 256 sharded lifecycle readers overlapping exclusive writers, writer preference and cancellation across colliding counters, shutdown, lock waits and online-index publication. Storage tests retain old views across flush/compaction, mix legacy and distributed references, check last-reference file closure and exercise 100 concurrent readers with colliding IDs during atomic two-key writes and compaction. Snapshot retention and owned values are checked together.

Prepared projection tests exercise repeated and coercing bindings, NULL/missing keys, residual predicates, pagination, BLOB/map/metadata ownership, invalid aggregates on empty answers, private writes, rollback, ALTER and table-name reuse. An internal regression confirms that the compiled projection is actually reused. All database and file artifacts use t.TempDir().

The required checks run locally with Go 1.22.2: root build, complete ordinary and race suites, go vet ./... and git diff --check. An initial verification attempt exhausted local disk space; old task-generated build-cache outputs were removed and local report copies compressed before rerunning the checks. Raw benchmark reports on test were retained.

See the benchmark documentation for both runners. Raw reports, resource counters, profiles, commands and source fingerprints are under /home/ubuntu/slopdb-bench/select-scaling-20261015/ on test. That directory also contains the human-readable report.md and a complete source-final.tar.gz snapshot with permanent tests, plus SHA256 metadata.
