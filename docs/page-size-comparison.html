Full methods, exact logical data/hash evidence, loading qualifications and raw artifacts are in the canonical report. The results below are historical performance evidence from an older 8 MiB-window configuration; they are not timings of the canonical storage fixtures.

Historical native footprint diagnostic

DuckDB’s 16 KiB TPC-C file is 571.78 MiB, versus 265.95 MiB at 64 KiB. Its reported 36,593 blocks include 36,586 used blocks and only seven free blocks: 0.109 MiB of free capacity. At 64 KiB all 4,255 blocks are used; at the 256 KiB control all 1,089 are used. VACUUM + CHECKPOINT left these inventories unchanged. The small-block penalty is therefore occupied block allocation, not a large freelist waiting to be reclaimed. Used blocks include indexes, metadata and internal slack, and are not equivalent to raw row payload. Per-column/index packing was not captured, so its precise cause remains open.

SlopDB lookup-heavy query regressions

Q05 6.819 31.168 1368.4 9994.9

Q12 2.426 17.104 388.9 5472.6

These queries use secondary indexes that do not contain all the requested lineitem values: Q5/Q7 use supplier access, Q6 ship-date access, and Q12 receipt-date access. Their saved EXPLAIN plans retain indexed access across page sizes for Q5/Q6/Q12; Q7’s outer EXPLAIN hides its derived join. The measured samples show increased elapsed time and cumulative allocation. The allocation deltas cover the whole Go process during execution, including background work, and do not measure cache hits or physical device I/O.

The code provides a plausible mechanism. On a decoded-cache miss, the SSTable reader allocates the stored block and decodes the entire compressed frame with DecodeAll, including rows unrelated to a point lookup. The fixed 128 MiB block cache has sixteen 8 MiB shards; larger decoded blocks leave room for fewer blocks in each shard. The access cost model weights noncovering lookups by row count with fixed factors of three through six; the join probe cost uses 4 + 3 * fanout. Neither model scales those costs with PageSize. It can therefore select similar lookup paths while the bytes decoded per miss grow. These are code-based explanations; the TPC-H reports contain no measured cache counters. Page-aware lookup costs, covering projections and scan/probe choices are candidates for further work.

Committed TPS is retained for completed runs alongside their transaction failure counts and status. SQLite contention can exhaust the common five-retry cap under its 250 ms writer-lock budget: those cells remain failed rather than clean throughput results, even when all thirty consistency assertions pass. Settings and failure classification were kept unchanged; failed reports are retained. DuckDB’s failed cells similarly exhausted the retry cap on optimistic write conflicts. Mean/p95/p99 latency samples contain only successful logical transactions, including retries before a successful commit. Failed, exhausted and canceled transactions are excluded, so SQLite’s low successful p95 does not describe the lock waits of its failed transactions.

Historical execution settings, validation and limits

The following settings describe the earlier 8 MiB-window execution/storage archive. Those jobs ran serially on the same machine. Load, preparation, validation, maintenance and close/reopen are outside transaction/query timing. OS caches are not reset. TPC-H uses one measured sample per query after one warmup at benchmarked sizes; its total sums twenty-two medians, each a single sample. SlopDB 1 MiB is explicitly excluded from query timing and query-answer checks. The TPC-H runner’s -load-only records the skip explicitly; its Q15 view is schema setup. TPC-C has one run per cell, which is descriptive evidence rather than statistical proof. Each storage size also comes from one fresh load. Equal SQL values do not imply identical internal sequence bytes or compaction/file boundaries, so footprint deltas are observed outcomes rather than a decomposition of codec efficiency alone.

WAL remains enabled and WAL fsync is disabled. SlopDB and DuckDB retain checkpoint and data-file synchronization; DuckDB bypass uses a Linux preload shim restricted to the exact benchmark WAL file. SQLite uses synchronous=OFF, which also disables checkpoint synchronization, so durability costs differ. SlopDB uses READ COMMITTED with row locks, SQLite serializes writers with BEGIN IMMEDIATE, and DuckDB uses snapshot isolation with optimistic conflict retries. These transaction and contention semantics also affect throughput.

SlopDB keeps its 4 MiB memtable, 128 MiB decoded-block cache and auto compression fixed. SQLite uses a 128 MiB cache budget per connection and an approximately 64 MiB automatic-checkpoint threshold, expressed in pages for each size. Timed TPC-C can open eleven SQLite connections; its aggregate cache allowance differs from SlopDB’s shared 128 MiB cache. DuckDB uses one execution thread and a 1 GB process memory limit. Budgets stay constant within each engine across page sizes; total memory allowances are not equal across engines. SlopDB’s default 64 MiB operator budget is a soft working-set estimate, not a process memory limit; results and some intermediate shapes still materialize. Page sizes describe different physical units: SlopDB's uncompressed variable-block target, SQLite's fixed B-tree page and DuckDB's persistent block. SlopDB blocks are compressed and are not padded to the requested target.

Sizes sum all regular database files after clean close, including indexes, catalog metadata and locks. Allocated totals use filesystem block counts, including directory blocks. Input data, reports, profiles and query spill files are outside the database directories. Large task-created databases were removed only after both validation phases and their per-file inventories were saved; source inputs and earlier databases were preserved. MiB means 1,048,576 bytes. Maintenance is SlopDB VACUUM, SQLite VACUUM, or DuckDB VACUUM followed by CHECKPOINT; these operations have different semantics. DuckDB VACUUM itself does not reclaim file space.

Every TPC-C storage value is checked after reopening and after maintenance. TPC-H checks all twenty-two complete answers against independently archived DuckDB results at benchmarked sizes, then checks them again after maintenance. The 1 MiB TPC-H load-only case verifies persisted row counts/schema and hash-verified source inputs; it does not verify every stored column or execute query-answer checks. Timed TPC-C requires all fifteen consistency assertions immediately after execution and after reopening. Expected rollbacks, shutdown cancellations and retries remain separate from unexpected failures.
