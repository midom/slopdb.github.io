Concurrent small-row SELECT benchmark

Build from the repository root and keep binaries, databases and raw reports outside the checkout:

mkdir -p ~/slopdb-bench
go build -o ~/slopdb-bench/select-bench ./cmd/select-bench
~/slopdb-bench/select-bench -dir ~/slopdb-small-row-10gb -seed-bytes 10000000000
python3 scripts/select_cache_matrix.py \
  --binary ~/slopdb-bench/select-bench --dir ~/slopdb-small-row-10gb \
  --output ~/slopdb-bench/select-cache-results

Add --policy clock and use a separate output directory to compare second-chance CLOCK with the default sampled LRU. Run each matrix serially with the same binary and seed. Both policies use 128 shards and identical byte budgets. The public storage option is Options.BlockCachePolicy (BlockCacheLRU or BlockCacheCLOCK); it changes eviction only and is not persisted in the database.

The cache uses mmap arenas by default. Add --memory heap to the matrix script, or -cache-memory heap to the benchmark binary, to use the Go heap cache. --memory mmap and -cache-memory mmap select the default explicitly. The public option is Options.BlockCacheMemory, with BlockCacheMmap and BlockCacheHeap. This setting does not change the database files.

Seeding refuses to overwrite a database. The fixture contains 39,062,500 rows of 256 logical bytes: two BIGINT values and a 240-byte deterministic BLOB. This is 10 decimal GB of logical data, excluding row tags, keys, SSTable metadata and compression. The persisted physical page target is 4 KiB. Loading uses the public SQL BulkInsert API in 4,096-row transactions and 256-row prepared INSERTs, with WAL enabled and WAL fsync disabled. A full VACUUM rewrites all levels into L6. Every typed row is checked after reopening before the seed is marked ready.

The cache matrix reuses those SSTables, with decimal decoded-block budgets of 100 MB, 1 GB, 10 GB and 20 GB. Each configuration opens a fresh process with 100 independent sessions and a shared prepared statement:

SELECT id,v,payload FROM small_rows WHERE id=?

Before timing, each process probes every eighth row. This warms full data pages; short trailing pages at file boundaries can remain cold. Small caches retain only their working budget. Then each session draws uniformly distributed IDs using its own deterministic PRNG. Every returned value is checked against the fixture generator. Validation time contributes to throughput; request latency covers the ExecPrepared call. Per-worker histograms use 16 subdivisions per power of two and report percentile upper bounds. Three consecutive 30-second samples share the warmed process cache; they are descriptive observations, not three independent fixture replications.

Per-sample process user/system CPU seconds are measured with getrusage, excluding warmup. AverageCPUCores is CPU seconds divided by elapsed seconds; CPUPercent divides that by the host's logical CPU count. Background Go GC work contributes to process CPU use. More CPU use alone is not a speedup.

Reports also record the runtime environment, timed GC cycles and stop-the-world pause seconds, and process voluntary/involuntary context-switch deltas. Compare CPU seconds per completed query and latency alongside throughput when increasing concurrency. GC pause time does not include concurrent collector CPU time. The JSON fields are RuntimeEnv, GCPauseSeconds, VoluntaryContextSwitches and InvoluntaryContextSwitches. Worker setup and sample-summary work are outside the allocation and GC measurement window.

Use -reuse-results to measure the existing Session.ExecPreparedInto API. Each worker keeps its own result destination and validates it before the next call. This reuses row maps, column slices and BLOB buffers; callers surrender the previous result contents on each call. The default still measures ExecPrepared, whose results can be retained independently. Keep the API mode fixed for code comparisons and label API-mode comparisons separately. Reports and runner manifests label the modes ExecPrepared (default, owned results) and ExecPreparedInto (reusable destination). Both matrix scripts accept --reuse-results; use separate output directories for the two modes.

To measure scaling at a fully fitting cache, run:

python3 scripts/select_scaling.py \
  --binary ~/slopdb-bench/select-bench --dir ~/slopdb-small-row-10gb \
  --output ~/slopdb-bench/select-scaling --policy clock \
  --workers 1 8 16 32 60 100 --cache-bytes 20000000000

Keep runtime settings (GOGC, GOMEMLIMIT, GOMAXPROCS) the same for code comparisons. Record tuning experiments separately, including their memory cost.

The scaling runner accepts --memory heap|mmap and --reuse-results. For example, to compare reader counts with reusable results and all 60 execution slots:

env -u GOGC -u GOMEMLIMIT GOMAXPROCS=60 python3 scripts/select_scaling.py \
  --binary ~/slopdb-bench/select-bench --dir ~/slopdb-small-row-10gb \
  --output ~/slopdb-bench/select-reuse-scaling --reuse-results \
  --workers 1 8 16 32 60 120 240

An mmap cache is outside the Go heap. A fully cached database can therefore leave a small live heap and trigger frequent GC while allocating fresh query results. Measure explicit GC headroom separately from library changes. A Go memory limit also excludes the anonymous cache mapping; assess whole-process RSS rather than treating that limit as a process memory ceiling.

For GOGC=200 alone, explicitly unset any inherited memory limit:

env -u GOMEMLIMIT -u GOMAXPROCS GOGC=200 python3 scripts/select_cache_matrix.py \
  --binary ~/slopdb-bench/select-bench --dir ~/slopdb-small-row-10gb \
  --output ~/slopdb-bench/select-clock-gogc200 --policy clock

The matrix records cache occupancy and hit/miss deltas, allocation, latency, throughput, process resource counters, exact commands, binary fingerprint and the SHA256 of every SSTable before and after the suite. It rejects failures, mutation of the seed, missing samples and cache-budget violations. Linux filesystem caching stays enabled and is never reset; these are engine-cache measurements and do not isolate physical device reads. A byte budget does not include all process memory or cache metadata. A 10 GB cache need not hold a 10 GB logical fixture once row/storage encodings are included.

Raw sample statistics also expose BlockCacheAdmissionSkips (best-effort admissions bypassed because a shard was busy) and PointIndexBytes (additional predecoded SSTable index-array capacity in the current file view). Index arrays are reader metadata outside the decoded-page budget. Older pinned views and other process allocations can retain more memory; use peak RSS alongside cache occupancy when comparing configurations. See the latest optimization report.

For diagnostic profiles, use a separate invocation and retain its flags. Do not mix its throughput into unprofiled results:

~/slopdb-bench/select-bench -dir ~/slopdb-small-row-10gb \
  -cache-bytes 100000000 -workers 100 -prewarm=false \
  -duration 15s -samples 1 -profile-dir ~/slopdb-bench/select-profile \
  -json ~/slopdb-bench/select-profile.json
go tool pprof -top ~/slopdb-bench/select-profile/cpu.pprof
go tool pprof -top ~/slopdb-bench/select-profile/mutex.pprof

For a separate TCP server process, add -debug-profiles to the server command. This enables standard /debug/pprof/ handlers on its loopback statistics listener, plus sampled mutex and blocking diagnostics. Request a CPU profile after the client's checked warmup, for example curl -o server-cpu.pprof 'http://127.0.0.1:33062/debug/pprof/profile?seconds=20'. Capture /debug/pprof/allocs, /debug/pprof/mutex, and /debug/pprof/block before and after that window; go tool pprof -base before.pprof after.pprof subtracts setup activity. These endpoints are disabled unless explicitly requested. Profiling runs measure diagnostics, not unprofiled throughput.

Setup, page-spaced warmup, seed validation, compaction and close are outside the timed samples. No loading or writes run alongside measurements. Benchmark timings are not ordinary test pass/fail thresholds; functionality tests use t.TempDir() and small fixtures.

Ordinary SQL and database/sql access

The same checked fixture supports these access modes:

Flags Access path
-api native -query-mode text Independent Session.Exec calls with literal SQL; parsing is timed
-api native -query-mode prepared Shared native prepared statement, independently owned results
-api native -query-mode prepared -reuse-results One reusable native result destination per worker
-api embedded -query-mode text Native embedded database/sql pool with literal SQL
-api embedded -query-mode prepared Native embedded pool with a shared prepared statement
-api mysql -query-mode text or prepared go-sql-driver/mysql over loopback TCP
-api mysql-lean -query-mode text or prepared Ordinal typed MySQL wire control with optional metadata disabled
-api pgx -query-mode text or prepared pgx database/sql adapter over loopback TCP
-api pq -query-mode text or prepared lib/pq over loopback TCP

Text queries have no bound arguments; pgx uses simple protocol with automatic statement caching disabled in text mode. Explicit prepared modes prepare before timing. Pools have one maximum open and idle connection per worker. Setup holds one result per connection until every connection is acquired, so connection opening and lazy per-connection preparation finish before measurement. Timed calls use the shared ordinary database/sql pool; query results are fully scanned, drained and closed before validation and the next request. Pool wait counts, open connections and checked answers are recorded.

The mysql-lean control negotiates standard CLIENT_OPTIONAL_RESULTSET_METADATA and CLIENT_DEPRECATE_EOF, then sets SESSION resultset_metadata=NONE before preparation. Each worker owns one connection and reusable packet/typed result buffers. It decodes this fixture's two BIGINTs and BLOB by ordinal without any column-definition packets. This is a fixture-specific protocol client with an empty-password slopdb login, not a general driver or a database/sql result. Reports label it typed-wire:mysql-lean:...; its missing shared pool overhead must be considered when comparing it with the ordinary mysql mode. It rejects unexpected metadata, malformed packets, extra rows, NULLs and incorrect values. Packets are bounded to 1 MiB, and input reads are buffered.

Without -endpoint, wire clients start an isolated protocol server in the same process as the benchmark. CPU and allocation counters then include both ends. The embedded driver wraps the already-open fixture through its non-owning connector. No network is involved in embedded access.

A dedicated external benchmark server can expose both protocols and report server counters separately:

select-bench -dir /tmp/select-seed -cache-bytes 536870912 \
  -serve-mysql 127.0.0.1:33061 -serve-postgres 127.0.0.1:54361 \
  -stats-listen 127.0.0.1:33062 -json /tmp/select-server.json

Readiness JSON records actual endpoints, PID and statistics URL. The server opens only the existing fixture, uses no TLS/compression, and shuts down on SIGTERM. Use a separate client process for each case:

select-bench -dir /tmp/select-seed -api mysql -query-mode prepared \
  -endpoint 127.0.0.1:33061 -server-stats-url http://127.0.0.1:33062/stats \
  -workers 60 -duration 10s -samples 3 -json /tmp/mysql-prepared.json

External clients never open the server's LSM directory. -dir supplies fixture metadata for validation. Client CPU/allocation counters exclude the server; ServerBefore/ServerAfter and server deltas are sampled outside each timed window through the optional statistics URL. Storage statistics in those reports come from the server. Keep server and client runtime settings, transport, cache, connection count and result-consumption behavior explicit when comparing modes.
