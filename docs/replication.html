SLOPDB / DOCUMENTATION / RAFT REPLICATION

Raft replication

SlopDB can run a replicated database using HashiCorp Raft. The leader ships atomic native WAL mutation batches containing row, index, catalog and allocation changes. The default sync mode acknowledges after a voting majority has durably stored its Raft entry and the leader has durably applied it to the native database. The optional async mode acknowledges after replication and application, then flushes a certified prefix periodically. It can lose recent acknowledged writes after a whole-cluster failure. Followers apply asynchronously. By default SQL is served by the ready leader. Followers and learners can opt into bounded-staleness or durable-barrier read-only SQL; writes still require the leader. There is no automatic SQL proxy.

Replication and clone/control connections support TCP and Unix sockets. They use separate listeners from the MySQL/PostgreSQL SQL listeners. A shared cluster token is mandatory; TLS and CA-verified mutual TLS are supported on both internal listeners, including Unix sockets. SQL authentication and TLS use their existing, separate protocol flags.

Start a cluster

Use a new node directory for each member. It contains local identity, native database generations, a durable Raft log and consensus snapshots. Do not pass an existing standalone database directory as the node directory.

export SLOPDB_RAFT_TOKEN='replace-with-a-long-random-shared-secret'

./slopdb --raft-id n1 --raft-bootstrap \
  --raft-listen tcp://127.0.0.1:9400 \
  --raft-control tcp://127.0.0.1:9401 \
  --raft-token-env SLOPDB_RAFT_TOKEN \
  --mysql-tcp 127.0.0.1:3306 ./node-1

Wait for Ready: true in the authenticated status response before cloning or connecting SQL clients. JSON field names are case-sensitive:

curl -H "Authorization: Bearer $SLOPDB_RAFT_TOKEN" \
  http://127.0.0.1:9401/v1/status

Start additional members with unique IDs and directories:

./slopdb --raft-id n2 \
  --raft-listen tcp://127.0.0.1:9410 \
  --raft-control tcp://127.0.0.1:9411 \
  --raft-join tcp://127.0.0.1:9401 \
  --raft-token-env SLOPDB_RAFT_TOKEN \
  --mysql-tcp 127.0.0.1:3307 ./node-2

./slopdb --raft-id n3 \
  --raft-listen tcp://127.0.0.1:9420 \
  --raft-control tcp://127.0.0.1:9421 \
  --raft-join tcp://127.0.0.1:9401 \
  --raft-token-env SLOPDB_RAFT_TOKEN \
  --mysql-tcp 127.0.0.1:3308 ./node-3

A joining node first downloads and verifies a committed database snapshot and its Raft membership metadata. The leader adds it as a nonvoter. Snapshot and WAL catch-up then proceed asynchronously without adding it to the voting quorum. By default, the leader commits a catch-up fence, checks the target's durable application checkpoint, and promotes it to a voter only after that fence is applied. Promotion intent is replicated and is resumed by a new leader. An unreachable learner remains a nonvoter. A three-voter cluster can continue with one voter unavailable; a two-voter cluster needs both voters.

Use --raft-auto-promote=false on the joining node to keep it a learner until explicit promotion. --raft-bootstrap is for the first member of a new cluster. On restart, retain the node directory, ID, Raft endpoint and control endpoint; omit the bootstrap and seed flags. Async restarts must contact a live quorum as described below; --raft-join can supply a leader discovery address. Bind port 0 is useful for tests, but restart must use the actual persisted port. Wildcard listeners require explicit --raft-advertise / --raft-control-advertise reachable endpoints.

To copy an existing standalone database into a new cluster, add --raft-seed /path/to/existing-db to the first bootstrap command. SlopDB opens that database exclusively, upgrades it if necessary, and takes a consistent backup into the new node directory. The seed is included in the initial Raft snapshot before learners or SQL clients are admitted. The original database remains a separate standalone database.

Replace --mysql-tcp with --postgres-tcp or a protocol socket flag to use PostgreSQL emulation or Unix SQL connections. With no SQL listener flags the process runs only the Raft/control services until SIGINT or SIGTERM; replicated mode does not run the stdin CLI or dot commands.

Replica roles

Full nodes join as temporary non-voting learners and can become voters after catch-up. Two additional persistent settings control voting and SQL storage:

Setting SQL tables and indexes Votes in quorum Can become leader
Default full replica Applied locally After promotion After promotion
--raft-non-voting Applied locally No No
--raft-logs-only Not materialized After promotion No
Both flags Not materialized No No

--raft-non-voting keeps a replica outside the quorum permanently. It overrides --raft-auto-promote and rejects explicit promotion. Full non-voting replicas can serve bounded-staleness or durable-barrier reads with the usual read flags. Their unavailability does not change the number of acknowledgments needed to commit. The existing --raft-auto-promote=false still creates a learner that an administrator can promote later.

For two materialized data copies and a third journal voter, start two ordinary full voting nodes as above, then start the third without SQL listener flags:

./slopdb --raft-id journal --raft-logs-only \
  --raft-listen tcp://127.0.0.1:9420 \
  --raft-control tcp://127.0.0.1:9421 \
  --raft-join tcp://127.0.0.1:9401 \
  --raft-token-env SLOPDB_RAFT_TOKEN ./node-journal

The journal joins as a learner and is promoted after validated catch-up, just like a full voter. Once all three are voters, a majority is two. Either full leader can commit with the journal while the other full voter is unavailable. The journal participates in sync WAL acknowledgments and async durability certification, but SQL reads/writes, SQL visibility waits and leadership transfers to it are rejected. Local election attempts cannot send pre-votes or votes; incoming votes from full candidates remain enabled. Direct Raft leadership-transfer requests are rejected as well.

A logs-only node retains complete consensus WAL payloads and opaque full recovery snapshots on disk. It validates snapshot checksums and every WAL command, but applies only replication metadata and checkpoints to its native store. It does not maintain SQL rows, indexes, catalogs or durable read views, and cannot generate an incomplete SQL snapshot. This saves application/LSM work; it is not a zero-data arbiter or a guarantee of smaller total disk usage. Full snapshot transfers still carry the recovery base. Journals do not generate application checkpoints or independently compact the retained WAL into SQL state; history after the last received full snapshot is retained. Plan disk capacity accordingly, or replace/re-clone the journal to refresh its base. Offline stable-point recovery can reconstruct SQL data from the journal's snapshot and retained WAL, even when full-node payloads are damaged; normal fencing/all-voter-source requirements still apply.

Raft's log freshness rule is unchanged. A full replica must have a sufficiently current log to win the journal's vote. If both full nodes are unavailable, or the only surviving full node is behind the journal and cannot catch up from the previous leader, the journal cannot become a temporary SQL leader. Restore a current full member or use the documented fenced recovery procedure. Ordinary commits promise a voting majority, not application to both full SQL copies. Async restarted voters, including journals, still require a live quorum for a fresh certified clone: restore quorum before taking another voter offline.

Native callers use Config.NonVoting and Config.LogsOnly. Node status and member status expose NonVoting and LogsOnly in addition to actual Raft Suffrage. These roles are persisted in the node identity; repeat the flags on restart. Changing roles requires a new node directory and membership replacement. Only a full voting node can bootstrap a cluster. Upgrade all nodes before using these roles; restricted-role directories use identity version 2 so older binaries cannot reopen them while ignoring their restrictions. Existing ordinary node identities and SQL/WAL formats remain compatible.

Bounded-staleness replica reads

Enable read-only SQL on a follower or learner by setting a local time bound:

--raft-replica-read-max-staleness 500ms

The Go equivalent sets Config.ReplicaReadMaxStaleness to 500*time.Millisecond. Zero, the default, keeps leader-only SQL. Negative values are rejected. Set the option on each replica that should serve reads, including on restart; it is a local admission setting, independent of the cluster's sync or async durability mode. Use the existing MySQL/PostgreSQL listeners or node.Database() SQL APIs. Applications connect to the chosen member directly. The option leaves reads on the ready leader linearizable.

Before serving a replica read, SlopDB asks the ready leader for a committed index, verifies leadership against a live voting quorum, and waits until the replica has actually applied that prefix to its native database. Concurrent readers share a refresh. The replica caches the proof for at most the configured bound, measured from the local start of the request, including RPC and catch-up time. This requires no synchronized clocks and appends no Raft entry. Leader control endpoints are replicated for discovery after restart or election. The authenticated POST /v1/read-index control endpoint accepts a member's ID, Address and Cluster; it rejects nonmembers and unavailable quorums. Internal token authentication and TLS/mTLS also protect these requests.

At statement snapshot acquisition, a successful read includes all transactions acknowledged before the proof request started. Thus it includes every commit older than the configured bound at that point, and may include newer commits. Freshness is checked again after waiting for snapshot access and loading the catalog. SQL metadata and data are captured together while FSM application is briefly excluded; execution and idle streaming cursors do not block replication. A long query, a stream's later rows, or a PostgreSQL portal's later fetches continue using that initial snapshot: the bound does not describe response age.

Ordinary SELECTs, compounds, CTEs, views, prepared/streaming queries, SHOW, read-only supported PRAGMAs and EXPLAIN of read queries are supported. Transactions and savepoints are read-only and retain READ COMMITTED semantics: every data statement takes a new bounded snapshot. DML, DDL, setting PRAGMAs, maintenance, locking reads (including nested queries/views) and COMMIT DURABLE require the ready leader. A normal replica COMMIT completes its read-only transaction; it does not confirm quorum health or durability. ROLLBACK remains available when a proof expires. Leadership changes and snapshot replacement invalidate sessions/prepared statements as before; reconnect and prepare again.

A cached proof may permit reads briefly during a partition. Once it expires, SlopDB refuses reads unless it can obtain a fresh quorum proof and apply its prefix within the bound. A changed term/leader, candidate role, recovering node, or fatal error also prevents using the old proof. Reads never fall back to unbounded staleness. The Go API returns replication.ErrReplicaTooStale when it cannot refresh/catch up within the bound; errors also preserve context cancellation/deadline causes. Role changes may instead return a leadership or recovery error. SQL clients receive an error with the same explanation.

Status keeps Ready reserved for writable leader admission and adds ReplicaReadMaxStaleness, ReplicaReadIndex, ReplicaReadProofAge and ReplicaReadReady. Duration fields are JSON nanoseconds. Read readiness reports a currently usable cached proof and can be false before the first read or after expiry; a subsequent read can refresh it on demand. Bounded reads use the live applied prefix, not necessarily a certified durable prefix in async mode.

Reading durable barriers

Choose a session policy before SELECTs:

SET READ BARRIER PREVIOUS;
SELECT * FROM accounts;

SET READ BARRIER NEXT;
SELECT * FROM accounts;

SET READ BARRIER DEFAULT;

PREVIOUS reads the most recent locally known, retained certified durable barrier. It does not contact the leader or wait for another flush. A replica can lag the leader's durable frontier; this policy promises durability rather than a wall-clock freshness bound. Rows and catalog metadata come from the same native MVCC snapshot, so an uncertified UPDATE, DELETE, new table, rename or ALTER cannot leak into the result even if already committed and applied.

NEXT requests a new barrier from the ready leader, waits for quorum durability certification and local application, and captures that certified snapshot (or a newer certified barrier if concurrent requests advance it). A new fence is created even when the cluster is idle. It includes writes committed before the request; later applied writes remain excluded until their own certification. The leader continues accepting writes while the captured prefix is being certified. There is one barrier request per SELECT, including streaming queries that need materialization. Open streams retain their original snapshot across subsequent barriers and compaction.

DEFAULT restores the node's configured default. COMMITTED explicitly selects the ordinary leader/bounded-staleness policy. On followers, COMMITTED still requires a configured positive --raft-replica-read-max-staleness; it does not turn on unrestricted local reads. The setting is private to the SQL session, works with MySQL and PostgreSQL (including prepared queries), and is not a transactional catalog change. Each statement in a read-only transaction takes its own selected barrier. Durable snapshot reads reject transactions with private writes, and locking reads require the normal leader execution path.

To make every read statement on a replica use a durable barrier by default, start it with one of:

--raft-read-barrier previous
--raft-read-barrier next

The Go equivalent is replication.Config{ReadBarrier: db.ReadBarrierPrevious} or db.ReadBarrierNext. This is a local admission policy, supplied again on restart. It enables read-only replica SQL without a staleness bound and also applies to reads on a node that becomes leader. Writes continue through the ordinary ready-leader path. With neither option, existing read behavior is unchanged. The policies work in both durability modes: sync-mode applied data is already durable, while async-mode reads exclude the applied suffix beyond D.

Go callers can override the policy for one execution with db.ExecOptions{ReadBarrier: db.ReadBarrierPrevious} / db.ReadBarrierNext, or use db.WithReadBarrier(ctx, mode) for streaming and prepared calls. An explicit minimum position must also be satisfied by the selected durable barrier: PREVIOUS fails if that position is newer; NEXT seals a prefix covering it. Logical commit-position responses continue to describe committed prefixes, not the historical snapshot selected by a read.

NEXT uses the authenticated internal TCP/Unix control service, including TLS/mTLS, and obeys query cancellation and deadlines. It fails if the leader or quorum is unavailable; it never falls back to PREVIOUS or the live applied state. PREVIOUS fails with replication.ErrDurableReadUnavailable if its exact view is not retained. Recovering async members remain fenced until re-cloning succeeds; the freshly certified clone supplies their initial durable view. READ COMMITTED session semantics and volatile/session expressions retain their normal behavior; these policies select the stored table/catalog view, not historical clock or physical configuration values such as PRAGMA page_size.

Raft fences are separate native publication boundaries. Each node retains its last published durable view plus at most eight in-flight fence candidates. Snapshots pin old row, index and catalog versions through compaction; a long interval between successful barriers can therefore retain more storage. A new certificate retires superseded pins, while open readers keep their own pins. Snapshot replacement, re-cloning and close release the generation's retained views. If a very late certificate's candidate was evicted, PREVIOUS reports an unavailable view; NEXT can establish a fresh one. Fence command encoding remains unchanged.

Status adds ReadBarrier, DurableReadIndex and DurableReadReady for the local retained view. The authenticated POST /v1/durability/read-barrier endpoint asks the ready leader to establish a new barrier and returns its token and, in async mode, its published certificate. Replica readers verify and install that certificate before using the corresponding native snapshot.

Logical commit positions and causal waits

A position is an opaque, signed token identifying a committed/applied Raft prefix in one cluster incarnation. It preserves full-width log indexes and terms. Treat the token as a string: do not order tokens lexicographically or construct them yourself. The same token is valid on every member sharing that incarnation and cluster key, including after snapshots/log compaction. Tokens from a cluster replaced by stable-point recovery are rejected.

Fetch the current position from the ready leader:

SHOW REPLICATION POSITION;

This returns one TEXT column, Position, after a fresh quorum check. It appends no log entry. The position includes previously acknowledged commits and may also include committed transactions whose responses are still in flight. It describes an applied prefix, not a count of replies received by clients.

Successful commits and autocommit writes return a position covering their transaction, possibly including concurrent commits published in the same or a later native batch. Buffered writes inside a transaction do not return a commit position. Native db.ExecResult.CommitPosition contains the token, and Tx.CommitWithPosition(ctx) returns it directly. Standalone databases leave that field empty. For wire clients:

  • PostgreSQL sends ParameterStatus(slopdb_commit_position, token) with explicit commit completion, or after an implicit commit and before ReadyForQuery. Existing command tags stay compatible. For pgx, use conn.PgConn().ParameterStatus("slopdb_commit_position") after commit/Sync.
  • MySQL includes slopdb_commit_position=<token> in the commit OK packet's info field. Clients negotiating CLIENT_SESSION_TRACK also receive the variable in the OK packet's system-variable state block. MySQL result sets using EOF framing, such as DML RETURNING, use the session lookup below instead.
  • SHOW LAST COMMIT POSITION retrieves the connection/session's last committed position, including when a driver hides wire metadata. It returns NULL before the first commit on that session. Use the same pinned connection; a pool can otherwise choose a different session. Rollback does not advance this value.

After receiving the token, connect to a replica with SQL reads enabled and wait before issuing the dependent read:

WAIT FOR POSITION 'token-returned-by-the-commit' TIMEOUT '5s';
SELECT * FROM accounts WHERE id = 1;

WAIT returns successful command completion with no result rows once the native application checkpoint covers the token. Receipt of logs alone is insufficient. The token and timeout accept prepared text parameters (? for MySQL/native, $1 and $2 for PostgreSQL). Timeout uses Go duration syntax and must be nonnegative; 0s polls without waiting. An omitted timeout uses the query's existing deadline, or the node's OperationTimeout (default 10s) when none exists. Query cancellation, connection/session shutdown and fatal node errors terminate waits. Invalid, modified or wrong-incarnation tokens fail with db.ErrInvalidPosition in Go. A wait timeout returns a deadline error rather than a successful timing result.

Waiting only proves local visibility. It neither appends a fence nor requires a new quorum, so an existing replica SQL session can finish a wait even if its bounded-read proof has expired. Subsequent data reads still follow the configured leader/bounded-staleness policy. A wait does not relax that policy or turn an old open cursor into a fresh snapshot. In async mode it does not fsync or certify D; use COMMIT DURABLE / WaitDurable for durable confirmation.

Go callers can use Node.AckedPosition(ctx) / Database.AckedPosition(ctx) and Node.WaitPosition(ctx, token) / Database.WaitPosition(ctx, token). To combine the wait with snapshot acquisition, attach the minimum to one call:

result, err := replica.Database().ExecContextWithOptions(ctx, query, db.ExecOptions{
    MinimumPosition: commitResult.CommitPosition,
})

db.WithMinimumPosition(ctx, token) supplies the same requirement to streaming QueryContext and prepared calls. The wait precedes the statement snapshot and normal consistency admission; failure prevents execution. These options require replication rather than silently ignoring a position on a standalone database.

Unix sockets

All internal endpoint flags accept unix:///absolute/path:

mkdir -p /tmp/slopdb-n1 /tmp/slopdb-n2
./slopdb --raft-id n1 --raft-bootstrap \
  --raft-listen unix:///tmp/slopdb-n1/raft.sock \
  --raft-control unix:///tmp/slopdb-n1/control.sock \
  --raft-token-env SLOPDB_RAFT_TOKEN \
  --postgres-socket /tmp/slopdb-n1/.s.PGSQL.5432 ./node-1

./slopdb --raft-id n2 \
  --raft-listen unix:///tmp/slopdb-n2/raft.sock \
  --raft-control unix:///tmp/slopdb-n2/control.sock \
  --raft-join unix:///tmp/slopdb-n1/control.sock \
  --raft-token-env SLOPDB_RAFT_TOKEN ./node-2

Socket files have mode 0600. On restart, a socket left by an unclean exit is reclaimed only if it refuses connections. Live sockets, regular files and symlinks are preserved. Socket parent directories must already exist.

TLS and certificates

Supply these flags to every node:

--raft-tls-cert node.pem --raft-tls-key node-key.pem --raft-tls-ca cluster-ca.pem

The CA bundle verifies outbound servers and requires inbound client certificates signed by that CA. Each node certificate must support both TLS server and client authentication, and its SANs must match the endpoints other nodes dial. The same node certificate is used in both directions. TLS 1.2 is the minimum. For Unix sockets the default verified server name is localhost; use --raft-tls-server-name cluster.example to select a common certificate DNS name. The override applies to all outbound cluster connections.

A certificate/key without a CA bundle enables server TLS with normal system-root verification outbound; the cluster token still authenticates Raft/control access. A custom/private CA needs the CA flag. Without TLS, token authentication does not encrypt database contents or HTTP control traffic; use plaintext only on trusted transports.

For control requests over TLS, use the HTTPS URL and supply the cluster CA, client certificate and key to curl. For Unix control sockets use curl's --unix-socket /path/control.sock with an HTTP(S) localhost URL.

Membership and status

Every control endpoint requires Authorization: Bearer <cluster-token>. Membership changes and snapshot exports must be sent to the ready leader.

Method and path Body / response
GET /v1/status Identity, cluster ID, role, leader, readiness, applied index/term, durability mode, durable index/term, recovery state and membership. Available on learners and followers.
POST /v1/read-index {"ID":"n2","Address":"tcp://host:9410","Cluster":"<cluster-ID>"}; quorum-confirmed committed index for a current member. Send to the ready leader.
GET /v1/snapshot Stream of Raft snapshot metadata and checksummed native state, used by clone bootstrap.
POST /v1/join {"ID":"n2","Address":"tcp://host:9410","Control":"tcp://host:9411","Cluster":"<cluster-ID>","AutoPromote":true}; target must already be running with matching identity. Normally called by --raft-join.
POST /v1/promote {"ID":"n2"}; waits for durable catch-up, then requests voting membership.
POST /v1/transfer {"ID":"n2"}; transfers leadership to an existing voter.
POST /v1/remove {"ID":"n2"}; removes a member. Transfer leadership before removing the current leader.
POST /v1/durability/read-barrier Request a new certified read barrier; returns its position and async certificate. Send to the ready leader.
POST /v1/durability/wait {"Cluster":"<cluster-ID>","Index":123,"Term":4}; waits for a certified durable prefix covering the token. Send to the ready leader.

For example, explicitly promote a learner:

curl -H "Authorization: Bearer $SLOPDB_RAFT_TOKEN" \
  -H 'Content-Type: application/json' -d '{"ID":"n2"}' \
  http://127.0.0.1:9401/v1/promote

Duplicate joins preserve existing voting membership. A node ID or Raft address already assigned to a different identity/address is rejected. Removing a member does not delete its directory. Stop a removed process and use a new identity and node directory when replacing it. There is no automatic address replacement or automatic quorum override. Async clusters have the explicit offline recovery procedure below.

Asynchronous durability

Set --raft-durability async on the bootstrap node. Joining members inherit the mode from the source; restarts inherit the persisted mode. Every member must use the same mode. An existing node cannot change its mode in place; seed a new cluster from a standalone backup to change modes.

./slopdb --raft-id n1 --raft-bootstrap \
  --raft-durability async --raft-durability-interval 100ms \
  --raft-max-durability-lag 1s \
  --raft-listen tcp://127.0.0.1:9400 \
  --raft-control tcp://127.0.0.1:9401 \
  --raft-token-env SLOPDB_RAFT_TOKEN \
  --postgres-tcp 127.0.0.1:5432 ./node-1

Two positions describe the log: R, the live applied prefix, and D, the certified durable prefix. Ordinary async-mode commits wait for Raft replication to a voting majority and leader application, without a per-commit WAL fsync. COMMIT ASYNC explicitly requests this behavior. Plain COMMIT and autocommit use the cluster's mode. In a sync cluster, COMMIT ASYNC retains sync guarantees.

COMMIT DURABLE waits until D covers the committed transaction and all preceding entries. It is supported over both MySQL and PostgreSQL, including prepared statements. Use it for transactions that must survive a full-cluster restart:

BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
COMMIT DURABLE;

The Go API also provides Tx.CommitDurable[Context], Node.CurrentToken, Node.DurableToken, Node.WaitDurable(ctx, token) and Node.FlushDurable(ctx). Tokens identify a cluster incarnation and log prefix. Store a durable token outside the cluster if disaster recovery must enforce a minimum restore point. COMMIT DURABLE returning db.ErrDurabilityUnconfirmed / SQLSTATE 40003 means the transaction committed but its durability confirmation failed. Rollback cannot undo it; reconcile its outcome before retrying.

Every flush commits a fence, synchronizes matching consensus-log prefixes on a voting majority, and stores a quorum certificate on a voting majority before advancing D. Certificates bind the cluster ID, term, membership and chained log hash. Native state can be reconstructed from a synchronized snapshot and this certified log. A regular flush holds membership fixed while later writes can continue beyond its captured prefix. Snapshot export also pauses proposals until its exact prefix has been certified and captured. Term/vote records and membership log records remain synchronously durable. WAL and its synchronization capability must stay enabled; the ordinary --no-wal-fsync and --no-wal flags remain invalid for replication.

Learner certificate delivery is asynchronous and does not extend voter-quorum completion. A leader keeps one latest pending certificate per current learner in one tracked delivery worker. Transient HTTP failures retry with cancellable 50 ms–1 s backoff and the configured operation timeout; newer seals coalesce without bypassing failure backoff. A learner can therefore publish an already certified durable read view after a lost notification, without requiring another write or Raft fence. Leadership/term changes and shutdown cancel pending requests and release their certificate references. These retries do not certify new data or append Raft entries.

Memtable rotation hands the sealed WAL to a background job for fsync and close, outside the storage writer and publication locks. Deferred writes can continue in the new WAL while that job runs. Durable writes used by receipts and certificates, storage.LSMTree.SyncReplicationWAL, and explicit storage flushes wait for the active WAL and every preceding sealed generation. Completion remains ordered even when individual file syncs finish out of order. Each generation's first sync also persists its directory entry. Background failures reject later writes and durability barriers, and shutdown joins all jobs and reports failures.

SSTable and manifest publication still synchronize before retiring WAL files. Background WAL fsync alone does not advance D or create a quorum certificate; ordinary async commits retain their existing recovery semantics. Sync commits continue waiting for the durable log prefix.

The default group-flush interval is 100 ms. The default maximum durability lag is the greater of one second and ten flush intervals. Once an unstable prefix exceeds that age, new writes are rejected until flushing succeeds. This limits continued admission during storage trouble; it is not a guaranteed recovery point deadline. Existing tentative writes remain at risk until D advances. Status exposes DurabilityError when periodic flushing fails.

An async process that restarts enters Recovering and cannot vote, elect itself, or serve SQL. It must download a freshly certified snapshot from a ready leader that verifies a live quorum before starting Raft again. Discovery uses control addresses in the last certificate and the optional --raft-join address. This prevents a restarted member from voting using a log that forgot updates. Membership promotion and exported snapshots also require a stable prefix.

Whole-cluster stable-point recovery

If no live quorum remains, async nodes stay in recovery even when their files appear intact. This also applies to a clean stop of every async member. Recovery is explicit and offline. To preserve all rows during planned shutdown, first stop SQL writes and membership changes, call FlushDurable, and record its durable token. A clean Close flushes local files but does not certify a new D.

  1. Stop or otherwise fence all original members, including originals of any copied directories. Prevent old clients and processes from rejoining.

  2. Gather offline node directories (or complete offline copies) from every voter in the latest certified configuration. Keep the original shared token. Recovery takes exclusive local locks but cannot fence remote originals for you.

  3. Export a new standalone seed. The positional directory is the first source; --raft-recovery-sources lists the others:

    ./slopdb --raft-token-env SLOPDB_RAFT_TOKEN \
  --raft-recover-to ./recovered-seed \
  --raft-recovery-sources ./node-2,./node-3 \
  --raft-recovery-fenced \
  --raft-recovery-minimum-token '{"Cluster":"OLD-ID","Index":123,"Term":4}' \
  ./node-1

    The minimum token is optional. Supply the token you recorded, not the example values. Recovery selects the highest valid certificate available, reconstructs exactly that prefix, checks its log hash, membership and database integrity, and refuses to restore behind the requested minimum. If no source has enough intact snapshot/log history, recovery fails and preserves its evidence.

  4. Bootstrap a new node directory with --raft-seed ./recovered-seed, then clone new members normally. The resulting cluster has a fresh incarnation ID; old durability tokens are rejected. The export contains RECOVERED_FROM.json and recovery marks supplied old roots RETIRED so they cannot be reopened as members. Keep them for investigation; never bypass the retirement marker.

The recovered database contains a complete transaction prefix, including rows, indexes, catalog changes and allocation state. Tentative entries after D are discarded even if some happened to survive locally. Durable certificates assume crash failures and trusted token holders; this is not Byzantine consensus.

Recovery and consistency

Each committed batch includes its cluster/index/term application checkpoint in the same native WAL record. Replaying an already applied index performs no write. Range tombstones are replicated alongside that checkpoint. Page-size changes through PRAGMA page_size are replicated; local compression and cache settings may differ. --page-size is rejected in replicated mode because it would make a local override outside consensus. Replication also rejects disabled WAL, disabled WAL fsync, disabled durable automatic-ID counters and index repair on open.

Snapshots pin a committed MVCC view and stream sorted raw keys with bounded batches. A SHA256 digest, ordering, cluster identity and replay checkpoint are verified before a fresh native generation becomes visible. The generation is fully flushed and synchronized, then CURRENT is atomically published. Async exports first seal their exact prefix. A crash before publication leaves the old generation usable; a crash after publication leaves the complete new generation. Sync-mode startup restores the consensus snapshot and replays subsequent committed Raft entries. A lagging learner whose logs have been compacted automatically receives a new snapshot through Raft.

Followers do not run local catalog migrations or index cleanup. A new leader first drains old SQL, commits a fence, reloads the persisted catalog and performs abandoned index cleanup through Raft before admitting clients. Existing sessions, open transactions and prepared plans are invalidated by leadership transitions; clients should reconnect and prepare again. On the leader, statements that access data capture Raft's committed index, verify leadership with a fresh quorum, and wait for actual native application of that prefix before execution. Read-only statements do not append log entries. Each leader data-access admission checks a quorum; no time-based leadership lease is used. Initial leader admission still commits a fence in the current term. Replica reads use the bounded proof mechanism described above.

Transaction control (BEGIN, COMMIT, ROLLBACK and savepoints) checks the ready leader role (or an enabled read replica role) and operates on session state. Every commit write still waits for Raft quorum replication and native application through the storage hook. A successful transaction-control response alone does not confirm quorum health; leader data-access statements and write acknowledgments continue to require a quorum.

Already committed WAL commands can share one native WAL record and, in sync mode, one fsync. The group's final checkpoint is published atomically with all its mutations before any of its commit futures complete. Control and membership changes remain ordered boundaries. Grouping adds no waiting timer and preserves individual Raft entries and SQL transaction boundaries.

Independent proposals encode outside the enqueue gate and enter Raft concurrently. SQL row, catalog and counter locks preserve dependent-write order; flushes and snapshots take the exclusive gate after preceding enqueues and their callbacks finish. Commands larger than 64 KiB are limited to one unresolved proposal at a time. The existing unbuffered Raft enqueue behavior is retained.

WAL commands and application checkpoints use specialized JSON writers/readers for their canonical shape, with standard JSON decoding for other representations. Their encoded bytes match the standard library, preserving existing transport and persisted history formats.

Local consensus-log records use a versioned binary encoding. Existing JSON log records remain readable and can coexist with new records in the same directory; the Raft transport, command payloads and history hash are unchanged. Older binaries cannot read newly written binary log records.

A lost-quorum node cannot acknowledge a write or serve linearizable reads. An opted-in replica can use an unexpired bounded-read proof or a retained PREVIOUS durable barrier as described above. A client that loses its connection or receives a leadership error during a commit can have an unknown commit outcome: the entry may still commit. Reconnect to the leader and reconcile using an application transaction/request identifier rather than blindly retrying a non-idempotent operation. Query cancellation does not retract an already proposed WAL batch.

This is single-database, single-leader replication. There is no multi-leader merge, sharding, automatic SQL routing, request deduplication or automatic disaster recovery. An encoded WAL command is limited to 64 MiB (JSON base64 framing adds overhead); an individual snapshot key/value record is limited to 256 MiB. The node's native data files need not be byte-identical because local MVCC sequence numbers, compression and compaction are independent. The replicated logical row/index/catalog bytes and transaction boundaries are preserved.

Go API

replication.Open(ctx, replication.Config{...}) owns the database and listeners. Use node.Database() for SQL, WaitReady for leader admission, Status for monitoring, and Join, Promote, TransferLeadership and Remove for membership. Done / Err report fatal application errors. Check node.Close() for storage flush failures; do not independently close or modify its database or native storage. StorageOptions configure local storage, and optional RaftConfig allows timing tuning; node identity, protocol version and snapshot recovery are controlled by the replication layer. Use the same SQL quoting mode on all nodes.

The lower-level storage and database replication hooks are for the replication owner, not application writes. A native standalone backup is not a replacement for a node's consensus state. Never copy another node's stable Raft log, vote, identity or node directory to create a member; use the clone/join path.
