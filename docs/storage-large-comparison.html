Historical matched-window storage measurements, 2026-10-12

Fresh SlopDB fixtures match the Zstd encoder window to each configured block target: 4 KiB, 16 KiB, 64 KiB or 1 MiB. Final sizes are measured only after VACUUM atomically merges and rewrites every SSTable, including existing L6 files, into L6. Every reopened report proves all L0–L5 file/byte counts are zero and records full_bottom_level_rewrite. L6 can contain several output files. Closed pre-maintenance sizes remain diagnostic inventories.

The datasets retain the original source hashes: 10,518,120 TPC-C rows across 256 warehouses (a replicated committed snapshot), and 1,731,999 TPC-H SF=0.2 rows with eight tables, fourteen indexes, ANALYZE and the Q15 view. Loading uses 4,096-row BulkInsert transactions and up to 256 rows per prepared INSERT. WAL remains enabled with WAL fsync disabled; SSTables and MANIFEST remain synced.

All eight fresh SlopDB cases measure loading/storage only. No TPC-H query pack or TPC-C throughput benchmark runs in this refresh, including at 1 MiB. TPC-C checks every row and column before/after maintenance; TPC-H checks persisted table counts against hash-verified source inputs, without full-column verification. Earlier timing results below used an 8 MiB window and are historical evidence.

SlopDB’s maintained 64 KiB footprints are 20.3% / 20.7% smaller than its fresh TPC-C / TPC-H 4 KiB controls. Native engine rows below are unchanged previous measurements, identified separately in the provenance paragraph.

Historical default-size comparison, 2026-10-11

All three engines were measured on larger, identical datasets for both workloads. Every database exceeds 100 MiB before and after maintenance. After maintenance, SlopDB uses less space than SQLite and DuckDB for the replicated TPC-C snapshot. For TPC-H SF=0.2, SlopDB is about 4.1% larger than DuckDB; SQLite is larger than both. These larger runs extend the small-dataset comparison.

Datasets and validation

TPC-H uses genuine DBGEN SF=0.2 inputs: 1,731,999 rows, including 1,199,969 lineitems and 300,000 orders. All engines load identical hash-verified inputs, the same eight tables, primary keys, fourteen secondary indexes, ANALYZE and Q15 view. SQLite uses an on-disk database. SlopDB and the DuckDB Go driver each completed all 22 queries without failures or timeouts. SQLite results matched both engines, and all answers also matched native TPC-H qualification results. All 22 queries were checked again for every engine after maintenance.

TPC-C uses 10,518,120 rows, including 8,216,320 order lines, 859,520 orders and 812,544 history rows. One committed benchmark snapshot was replicated 128 times into 256 disjoint warehouses. Warehouse references and history IDs were shifted consistently; the 1,000-item catalog is shared. All three engines use the same values, declared primary keys and customer/order index. Every value was compared after reopening and again after maintenance. Repeated snapshot values can affect compression; this is an equal-data storage comparison rather than a new timed transaction throughput run.

The large SlopDB validation pass exposed a planning gap for simple SELECT queries using BETWEEN on composite primary keys. Equivalent >= / <= predicates, primary-key ordering and a limit of expected rows plus one enabled bounded validation reads. Exact table counts and every expected value were still checked. This adjustment applied to the validation helper during the storage measurements. The 22 TPC-H query definitions are the existing repository query pack. No production SQL or storage code was changed for those measurements.

The planning gap is now fixed: the shared tuple planner extracts inclusive integer bounds from BETWEEN, including signed literals and prepared parameters, for composite primary keys and secondary indexes. The original predicate remains a residual check to preserve mixed-type and NULL behavior when only one bound is usable. NOT BETWEEN and disjunctive predicates retain their existing paths. On this database, selecting 20 order lines from warehouses 129–130 took 11,366.934 / 11,103.007 ms before the fix and 1.149 / 0.140 ms after it. Answers were identical. These are first/repeated execution samples from separate CLI processes; OS caches were not reset. See the query measurement.

Settings and evidence

SlopDB used f45ea982792cd25c94478b76dd4bf20ac83bb8eb, Go 1.22.2, a 4 MiB memtable, 4 KiB blocks and default auto compression. DuckDB is 1.5.6; its TPC-H Go runner uses one execution thread and a 1 GB memory limit. New SQLite files use Python SQLite 3.45.1. WAL remains enabled and WAL fsync is disabled during new loads. DuckDB uses the existing Linux preload shim restricted to each benchmark's exact WAL file; other checkpoint/file syncing stays enabled. Files were synced after close before recording final filesystem allocation.

Load, validation and maintenance jobs can overlap. Saved query timings are diagnostic; this run establishes storage footprints and correctness rather than a controlled throughput comparison. Database directories and input hashes are recorded in the raw size report, along with exact per-file apparent bytes, allocated bytes, row counts, SSTable levels, page/block statistics and validation status. Allocated directory totals were independently checked using du -s -B1.

Full query reports: SlopDB and DuckDB. See the TPC-H runner and TPC-C comparison runner for schemas and workload definitions. Large inputs and databases remain outside the repository under the paths recorded in the reports.
